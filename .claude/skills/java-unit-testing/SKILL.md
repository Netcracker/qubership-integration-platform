## Default test style

Prefer plain JUnit 5 + Mockito unit tests by default.

Use plain unit tests when:

* the class can be instantiated directly
* dependencies can be mocked or replaced with real lightweight objects
* config values can be set directly
* CDI wiring is not the subject
* Quarkus runtime behavior is not required
* the test verifies ordinary Java logic, mapping, validation, fallback, or interaction behavior

For ordinary Mockito unit tests, use:

```java
@ExtendWith(MockitoExtension.class)
@DisplayNameGeneration(DisplayNameUtils.ReplaceCamelCase.class)
class SomeServiceTest {
}
```

Use test method names in `shouldXWhenY` format.

Never add Arrange / Act / Assert comments.

## Test type decision

Choose the lightest test type that proves the behavior.

Use plain JUnit 5 + Mockito as the default.

Use `@QuarkusComponentTest` when:

* Quarkus-filled `@ConfigProperty` values are the behavior under test
* a small CDI/component-level test is enough
* the component can be tested safely without full application startup
* `@TestConfigProperty` makes the test clearer than reflection or manual field mutation

Avoid `@QuarkusComponentTest` when:

* normal-scoped beans require unsafe field mutation
* `@Startup` creates side effects
* global JVM state makes the test unstable
* `System.getProperty(...)` or static state makes the test order-sensitive
* a plain unit test can verify the same behavior more directly

## Mockito rules

Keep Mockito strict.

Avoid:

* unnecessary stubs
* broad `lenient()` usage
* over-stubbing
* stubbing behavior that is not used by the current test
* stubbing common behavior in `@BeforeEach` when only one or two tests need it
* mocking simple value objects when real objects make the test clearer

Recommendations:

* Use `lenient()` only for unavoidable shared infrastructure stubs.
* When Mockito reports `UnnecessaryStubbingException`, remove or move the unused stub instead of silencing it.
* When Mockito reports `PotentialStubbingProblem`, check whether production code calls a different overload, different argument, or different object instance than the stub expects.
* Prefer local stubbing inside each test when it keeps strict stubs clear.
* Use `@BeforeEach` for common stubs only when they are used by every test or are genuinely part of stable fixture setup.
* For `anyMap()`, use explicit generic type arguments when needed:

```java
Mockito.<String, Object>anyMap()
```

## Prefer real objects when practical

Prefer real objects when they make the test simpler and more honest.

Common examples:

* real maps, lists, metadata objects, and value objects
* real mapper/configuration/domain objects when they are lightweight
* real `ObjectMapper` for normal JSON serialization/deserialization behavior
* real project-helper-created Camel exchanges when Exchange state matters

Mock only what is external, expensive, unstable, or intentionally controlled by the test.
Mock `ObjectMapper` only for targeted exception, fallback, or error branches.
Use spies only when they are clearly simpler than full mock setup.

## Coverage work

When improving JaCoCo coverage:

* focus on meaningful branches and behavior
* cover fallback, validation, null, empty, overwrite, exception, and boundary cases
* rewrite entire test files only when necessary
* prefer adding focused tests to existing test classes

When a coverage report points to missed branches:

1. inspect the target production code
2. inspect existing tests
3. identify genuinely useful missing behavior
4. add the smallest focused tests
5. run the relevant test class if possible

Avoid chasing 100% coverage with artificial tests.

## Maintainability baseline

Tests should survive reasonable refactoring when external behavior remains unchanged.

Treat these as warning signs:

* excessive `mockStatic(...)`
* reflection-based access with `getDeclaredField(...)`
* `setAccessible(true)`
* assertions against private fields
* assertions against internal builder state
* tests that verify implementation steps instead of externally visible behavior
* tests that require changing private method names, private field names, or internal object structure

Before adding a brittle test, check whether the same behavior can be verified through public methods, returned values, emitted events, Exchange headers/properties/body, configuration objects, dependency interactions, thrown exceptions, or persisted/published state.

## Static mocking and reflection baseline

Static mocking is allowed, but it is not the default.

Before using `mockStatic(...)`, check whether one of these options is cleaner:

* use a real object
* inject a dependency
* use an existing project helper
* test through public behavior
* move static access behind a small wrapper/factory/provider
* pass a controllable collaborator into the class under test

When static mocking is necessary:

* use try-with-resources
* keep the scope as small as possible
* do not share static mocks between tests
* verify only meaningful behavior

Avoid reflection in new tests. Use reflection only when no stable public behavior exists and the user explicitly wants coverage for that legacy branch.

## Workflow before editing

Before editing tests:

1. inspect the target production class
2. inspect the existing test class if present
3. inspect nearby tests in the same package/module
4. identify the local test style
5. load only the relevant reference files
6. check for shared helpers before adding local helpers
7. choose plain unit test or `@QuarkusComponentTest`
8. identify missing behavior and branches
9. plan small focused changes

Before adding a brittle test, ask:

* Am I verifying public behavior or private implementation?
* Am I adding reflection only because it is convenient?
* Am I adding `mockStatic(...)` because the design is hard to test?
* Would a small wrapper/factory/provider make the behavior easier to test?
* Is this async test deterministic?
* Will this test leave threads, schedulers, timers, static mocks, or global state behind?
* Will this test still be valid after a harmless internal refactoring?

If the answer reveals a design-for-testability issue, mention it in the summary and ask for explicit permission before changing production code.

## Workflow while editing

When editing:

1. preserve existing test style
2. add focused tests
3. keep helper methods narrow
4. avoid broad rewrites
5. avoid production changes unless explicitly requested
6. keep Mockito strict
7. prefer real objects where they reduce mocking complexity
8. reuse project helpers
9. keep async tests deterministic
10. keep static mocks and reflection out of new tests unless justified

### Maven command selection

For local agent execution, prefer Maven Wrapper when it exists.
Use the wrapper command that matches the current operating system and shell:

* Linux, macOS, Git Bash, or WSL:

  ```bash
  ./mvnw -q -B -Dstyle.color=never -f <module>/pom.xml -Dtest=<TestClassName> test
  ```

* Windows PowerShell:

  ```powershell
  .\mvnw.cmd -q -B -Dstyle.color=never -f <module>/pom.xml -Dtest=<TestClassName> test
  ```

* Windows cmd:

  ```cmd
  mvnw.cmd -q -B -Dstyle.color=never -f <module>/pom.xml -Dtest=<TestClassName> test
  ```

Use Maven Wrapper for local agent test execution only. When Maven Wrapper is absent, discover the available Maven command instead of assuming `mvn` is available in `PATH`.

Use this fallback order:

1. system Maven
2. Maven from `MAVEN_HOME`
3. Maven from `M2_HOME`
4. Maven command documented in repository README, CI configuration, scripts, or previous successful local test runs
5. IDE-bundled Maven only as a last local fallback

Do not hardcode user-specific IDE paths, home directories, or OS-specific paths unless no standard Maven command is available and the path exists in the current environment.
When using a non-standard Maven binary, report the exact binary path in the final summary.

### Focused unit test execution

For Maven modules, infer the module from the file path and nearby project structure.

Use `-f <module>/pom.xml` or `-pl <module>` according to the repository’s existing local command style.

Prefer `-f <module>/pom.xml` when the test belongs clearly to one module and this is consistent with nearby successful local commands.

Example with Maven Wrapper:

```bash
./mvnw -q -B -Dstyle.color=never -f micro-engine/pom.xml -Dtest=CustomGooglePubSubEndpointTest test
```

Example without Maven Wrapper:

```bash
mvn -q -B -Dstyle.color=never -f micro-engine/pom.xml -Dtest=CustomGooglePubSubEndpointTest test
```

Alternative module style:

```bash
mvn -q -B -Dstyle.color=never -pl micro-engine -Dtest=CustomGooglePubSubEndpointTest test
```
If the first command fails because the tool is missing, treat it as build-tool discovery failure, not as a test failure. Discover another available runner and retry the same smallest relevant test scope.

### Quiet output and warnings

Use:

```bash
-q -B -Dstyle.color=never
```

for Maven test commands unless the user asks for verbose output.

`-q` reduces Maven log output, but it may not suppress:

* JVM warnings
* dependency download messages
* Mockito inline mock-maker warnings
* Byte Buddy agent warnings
* Quarkus or toolchain warnings printed to stderr

* Use the process exit code and Surefire/Failsafe failure summary to determine whether tests passed.
* If the command output is quiet and does not show an explicit success summary, check or report the exit code.
* On Unix-like shells, this is acceptable for local verification:

```bash
./mvnw -q -B -Dstyle.color=never -f <module>/pom.xml -Dtest=<TestClassName> test; echo "exit_code=$?"
```

If tests fail, inspect the first meaningful compiler, Checkstyle, Surefire, Failsafe, or assertion error.

Do not read, summarize, or paste the full Maven log when the quiet output already identifies the failure.

### Coverage report execution

* Run coverage commands only when the user asks for JaCoCo, coverage progress, coverage report generation, or coverage verification.
* Do not run full coverage commands for an ordinary single-class unit test task.
* Use `test` for focused single test-class verification.
* Use `verify` when JaCoCo report generation is required by the Maven lifecycle.
* Use `clean verify` when the user asks to regenerate coverage from a clean state.
* For Quarkus modules in this repository, use the development profile required by the project.

With Maven Wrapper:

```bash
./mvnw -q -B -Dstyle.color=never -f <module>/pom.xml clean verify -Dgpg.skip -Dquarkus.profile=development,no-dbaas,no-m2m
```

Without Maven Wrapper:

```bash
mvn -q -B -Dstyle.color=never -f <module>/pom.xml clean verify -Dgpg.skip -Dquarkus.profile=development,no-dbaas,no-m2m
```

Add `-Dquarkus.profile=development,no-dbaas,no-m2m` only for Quarkus modules.

Do not run broad coverage commands unless the user asks for coverage or the change is risky enough to justify it.

After coverage generation, report:

* command run
* whether it was a Quarkus or Spring Boot module
* whether JaCoCo report generation completed
* report path if visible from Maven output or known module structure
* any test, Checkstyle, compilation, or environment failure

## Output expectations

When reporting back, include:

* tests added or changed
* behavior or branches covered
* command run
* test result
* any remaining risk or follow-up

Keep the summary concise and practical.

Report brittle-test or flaky-test findings separately from normal test additions.

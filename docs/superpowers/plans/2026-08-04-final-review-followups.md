# Final-Review Follow-ups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the two findings from the third whole-branch final review of the Istio migration branch that the human directed a fix for: micro-engine's new route-unregister-on-shutdown deletes routes that still-running replicas need, and a stop-time route-removal failure in `engine` now leaves the Camel context running forever instead of stopping it.

**Architecture:** Task 1 reverts a specific piece of this branch's own earlier micro-engine work (deletes the route-unregister action and its now-dead supporting method) rather than adding new guard logic, per explicit human direction: micro-engine never removed routes on shutdown before this branch, and it shouldn't now — for Istio, HTTPRoute CRs for micro-domains will be generated by runtime-catalog alongside the domain's other CRs, not registered/unregistered by micro-engine at runtime. Task 2 makes `IntegrationRuntimeService.stopDeploymentContext` guarantee the Camel context is always stopped, even when a stop action throws, by catching the throw, running the existing cleanup/stop sequence unconditionally, then rethrowing so the deployment's failure status and logging are unchanged. Task 3 corrects the original Istio design spec's now-disproven redeploy-ordering claim, the root cause that produced two rounds of Critical bugs (C1/C2, then C-1/I-1) before it was corrected in code.

**Tech Stack:** Java 21 (`engine`), Java 21 + Quarkus/CDI (`micro-engine`), JUnit 5, Mockito (`mock(Class)` factory style for `engine`; `@ExtendWith(MockitoExtension.class)` + `@Mock` for `micro-engine`, matching each module's existing test conventions).

Before this branch, micro-engine never unregistered routes on shutdown at all; this task restores that. For Istio specifically, HTTPRoute CRs for micro-domains will be generated by runtime-catalog alongside the domain's other CRs (a build-time/deploy-time concern, not a micro-engine runtime concern) — so no micro-engine runtime code is needed for the Istio path either now or later.

### Task 2: Guarantee the Camel context stops even when a stop action fails

**Files:**
- Modify: `engine/src/main/java/org/qubership/integration/platform/engine/service/IntegrationRuntimeService.java`
- Create: `engine/src/test/java/org/qubership/integration/platform/engine/service/IntegrationRuntimeServiceTest.java`

**Interfaces:**
- Changes `stopDeploymentContext`'s visibility from `private` to package-private (no modifier) so a same-package test can call it directly. No other signature changes; all three existing call sites (`stop()`, `update()`, `removeOldDeployments()`) are unaffected by the visibility change and need no edits.

`stopDeploymentContext` (`IntegrationRuntimeService.java`, currently lines 713-723) calls `deploymentProcessingService.processStopContext(...)` before `context.stop()`. `DeploymentProcessingService` has no try/catch anywhere in its action-dispatch path, so when a stop action throws (as `RemoveRoutesFromControlPlaneAction` now does via `RouteRegistrationException` on a control-plane failure), the throw propagates out of `stopDeploymentContext` before `context.stop()` ever runs. On undeploy the context was already removed from the cache moments earlier, so it becomes both unreachable and still running. This task makes the cleanup-and-stop sequence run unconditionally, then rethrows the original exception afterward — the deployment still ends up reported as failed exactly as it does today (this task does not change that), but the Camel context is actually stopped.

    void stopDeploymentContext(SpringCamelContext context, DeploymentInfo deploymentInfo) {
        RuntimeException stopActionFailure = null;
        try {
            deploymentProcessingService.processStopContext(context, deploymentInfo, null);
        } catch (RuntimeException e) {
            log.error("Deployment processing actions on context stop failed for deployment {}: {}",
                deploymentInfo.getDeploymentId(), e.getMessage(), e);
            stopActionFailure = e;
        }
        if (nonNull(context)) {
            quartzSchedulerService.removeSchedulerJobsFromContexts(
                Collections.singletonList(context));
            if (context.isRunning()) {
                log.debug("Stopping context for deployment: {}", deploymentInfo.getDeploymentId());
                context.stop();
            }
        }
        if (stopActionFailure != null) {
            throw stopActionFailure;
        }
    }

The `nonNull(context)` block, the `quartzSchedulerService` call, and the `context.isRunning()`/`context.stop()` logic are byte-for-byte unchanged — they just now always run before the exception (if any) propagates.

### Task 3: Correct the disproven redeploy-ordering claim in the original design spec

**Files:**
- Modify: `docs/superpowers/specs/2026-07-31-istio-routes-registration-service-design.md` (lines 44-49, or the current location of the same paragraph if line numbers have drifted)

Before editing, invoke the `english-developer-style` skill per this repo's `.claude/rules/english-developer-style.md` — it applies to any edit to this design-doc prose, regardless of length.

The current text asserts `RemoveRoutesFromControlPlaneAction` "always runs before `RegisterRoutesInControlPlaneAction`" on a redeploy and concludes neither caller needs to separately account for silently dropped paths. Both halves are false: `IntegrationRuntimeService.update()`'s actual order is register (new deployment) → start (new context) → stop (old deployment) — register runs first, not stop. This false premise produced two Critical bugs across two review rounds (C1/C2, then C-1/I-1), both fixed by the `ChainRouteRegistry` work documented in the two later specs.

- [ ] **Step 1: Replace the paragraph**

Find this exact paragraph (currently at lines 44-49; search for the text if line numbers have drifted):

```
**Redeploy ordering:** on a chain redeployment, `RemoveRoutesFromControlPlaneAction`
(stop, on the *old* deployment context) always runs before
`RegisterRoutesInControlPlaneAction` (register, on the *new* context) — so a
route dropped entirely from a chain (not moved to another tier, just deleted)
is already cleared by the stop step before the new registration posts. Neither
caller needs to separately account for "silently dropped" paths.
```

Replace it with:

```
**Redeploy ordering:** on a chain redeployment, `RegisterRoutesInControlPlaneAction`
(register, on the *new* context) runs before `RemoveRoutesFromControlPlaneAction`
(stop, on the *old* context), not the reverse. `ChainRouteRegistry` handles the
resulting overlap: it tracks every currently-registered deployment per chain, and
a stop action removes only the paths no other registered deployment still claims.
A route dropped entirely from a chain (not moved to another tier, just deleted) is
still cleared correctly, since no other deployment claims it either. See
`docs/superpowers/specs/2026-08-03-chain-route-registry-design.md` and
`docs/superpowers/specs/2026-08-03-chain-route-registry-multi-registration-design.md`
for the full mechanism.
```

# Error Handling

## Description

---

### Overview

Cloud integration Platform exposes its capabilities to the external (within CLOUD) consumers in a synchronous (REST API via HTTP) and asynchronous (Kafka, RabbitMQ) ways. During the processing, errors of different kinds might happen, hence it is essentially to have a mechanisms that helps to:

- Fetch the errors
- Transform them to human-readable format (and put them in the response for REST API)
- Store them for future analysis

> ℹ️
> Please note, that users might configure their own error handling rules and error formats in the chain. This section only contains CIP-specific logic description.

Also, for REST APIs, that are exposed via gateway, error handling of the gateway will be applied before **CIP**, hence it is not described in the current article.

### UI Errors

During work in Cloud Integration Platform application, user might face with an errors happened because of invalid settings or internal errors, that require more close verification.

Each notification consists of next parts:

- **Header:** mandatory short description of the error (e.g. "Failed to delete element").
- **Description:** mandatory text for the user, that contains explanation of what happened and what could be done to resolve the issue (if known).
- **Show Details:** optional details that available via "Show Details" link, where CIP contains details for developers.

![Error notification example]

Each page with error details consists from next parts:

- **Header:** Always "Error Details"
- **Originating Service:** Service name that handled the error event. Next service names are available:
  - Engine
  - Variables
  - Catalog
  - Services
  - Sessions
  - UI
- **Timestamp:** Timestamp for error event, in a format of yyyy-mm-dd hh:mm:ss:mmm
- **Message:** Human-readable error message.
- Button "**Download**": button that allows user to download text file with error details.
- Button "**Copy**": button that allows to copy error details to clipboard.

### General Logic

This section describes error structure, that shall be considered by other parties that are utilizing **CIP Chains.**Cloud Integration Platform follows message structure, introduced in the main error handling article: [Error Codes Development Guide] and utilizes [TBD] core library to build a response message for runtime operations.

> [!CAUTION]
> CIP is not responsible for finalized message to the **business** user, it provides calling system with the response with technical data. If technical data in the CIP response shall be altered, then it is chain owner/calling system responsibility to do so, as CIP does not have any contract with final system.

#### Error Structure

Cloud integration Platform will return JSON message with content-type: application/json

| name             | type   | mandatory | description                                                                                                                                                                                   |
|:-----------------|:-------|:----------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| code             | String | true      | Unique CIP code. <br/> Format: CIP-xxxx (where xxxx is a numeric code identifier)                                                                                                             |
| reason           | String | true      | Error title in a plain text format. Does not change from error instance to instance and does not contain context of the error and secure information. <br/> MD/AsciiDoc syntax is prohibited. |
| message          | String | true      | High-level error details in a plain text format. Context related information of particular error instance. <br/> MD/AsciiDoc syntax prohibited.                                               |
| extra            | Object | false     | Object, that contains additional technical data, if there is any. Controlled by library: [TBD]                                                                                                |
| validationResult | String | false     | Contains details of failed validations. Usually available for codes: CIP-0100, CIP-0112                                                                                                       |
| sessionId        | String | false     | Failed session's identifier.                                                                                                                                                                  |
| failedElementId  | String | false     | Failed element's unique identifier.                                                                                                                                                           |

#### Technical Headers

There are technical headers, that shall be considered during configuration of the chain (especially when working with [Headers Modification], [Mapper], [Script] and almost any of [Senders] elements). Technical headers are always stored in context and might be "**reinstated**" via option "**Propagate context**", described for each particular sender element (on the respective page), where option is available.

Values of technical headers **could be overridden ONLY in** **the sender elements** (besides some few elements that don't have an option to work with the headers at all) and not available for modifications in **transformation elements**, mentioned above. When updating the values, pay attention to the order of the element in the chain and usage of "**Propagate context**" flag (e.g., when respective option is selected, propagated values in [Service Call] will override the ones, configured within the previous elements, even if such headers were requested to be removed).

It shall be also noted that [Retry Session from the Middle] functionality will consider original values of technical headers and only pass original values during retries.

List of technical headers is available by next link: [TBD] (managed by non-CIP team).

# Generated snapshot coverage

The generated suite imports [test configurations](../integration-build-pipeline/src/test/resources/testConfigurations),
builds their XML through integration-build-pipeline, and executes that XML in micro-engine.
The matrix records assertions defined in the manifests. Test reports determine whether those
assertions pass. Listing an element type does not imply coverage of all its options or protocols.

A scenario ID is scoped to its manifest. Links below identify the manifest; exact scenario IDs can be used with
`snapshot.target` and `snapshot.scenario`. Structural child types share a row with the element that executes them.

The Kafka sender manifest groups seven chains. Each of its 29 scenarios selects one deployment and starts one broker;
the full suite defines 183 scenarios while avoiding unused deployments and fixtures.
Kafka sender scenarios contain 263 invocations: 18 Short invocations and 245 across 28 Long scenarios.
Compatible cases share a broker and route while preserving
their individual assertions and recovery checks. The runner stops a scenario at its first unexpected failure.

The RabbitMQ manifest groups 89 invocations into four scenarios across three exported chains.
The functional chain retains four independently configured sender routes. Its 18 Short and
47 Long invocations select their respective entrypoints and share one broker per scenario.
The broker failure scenario contains 22 invocations; the MaaS scenario contains two.
Each invocation checks delivery and verifies that inactive senders did not attempt a send.

The Pub/Sub manifest groups 28 invocations into three scenarios for one exported chain:
two Short invocations, 25 Long invocations sharing an emulator and publisher, and one
OAuth rejection invocation with an empty credentials cache. The combined Long scenario
refreshes its token first, recreates the topic after publication and recovery checks,
and deletes the topic at the end.

## HTTP sender composition

The four HTTP sender exports contain 20 senders. Two entrypoints in
`http-sender-context` check multiple senders in the same exchange. Their script
resources record HTTP errors and route completion without replacing message bodies
or headers. Both routes use internal calls, context propagation, connection reuse,
and disabled M2M. Their timeouts are 5000 ms unless specified below.

### Sequential senders

Entry point name: `http-sender-sequential-context`.
Topology: `Chain Trigger -> Sender A -> Sender B`.

| Setting | Sender A | Sender B |
| --- | --- | --- |
| Method | POST | PUT |
| URI | `http://snapshot-http.invalid/sequential/first?step=first` | `http://snapshot-http.invalid/sequential/second?step=second` |
| Context override | `X-Request-Id: first-hop` | None |
| Correlation position | Header | Body |
| Correlation name | `X-Correlation-Id` | `requestId` |

Five invocations check that A receives the overridden request ID and B receives
the original ID. A's JSON response becomes B's request body. Its response correlation
header supplies B's outgoing body correlation ID; B's response supplies the final ID.
Assertions check each sender's method, path, query, and request count. When A fails,
B receives zero requests. Errors from either sender are followed by a successful
invocation through both senders.

### Caught HTTP errors and fallback

Entry point name: `http-sender-caught-error-fallback`.
Topology: `Chain Trigger -> Try-Catch-Finally -> completion marker`.

- Try: Sender A, followed by a script that sets `tryCompleted` to `true`.
- Catch: a script that sets `atCatch` to `true` and copies the HTTP status and body
  to `caughtStatus` and `caughtBody`, followed by Sender B.
- Finally: a script that increments `finallyCount`.
- After the container: a script that sets `completed` to `true`.

Catch handles `org.apache.camel.http.base.HttpOperationFailedException` with
priority `0`. Sender A uses POST to
`http://snapshot-http.invalid/recovery/primary?step=primary`, a `1000` ms timeout,
and the context override `X-Request-Id: primary-hop`. Sender B uses POST to
`http://snapshot-http.invalid/recovery/fallback?step=fallback` without a context override.
The scripts record state without replacing the message body or its headers.

Six invocations check successful primary calls, caught HTTP errors followed by a
successful fallback, fallback errors, uncaught transport errors, and recovery after
the propagated errors. Assertions check the captured error status and body, which
senders ran, the final result, and exactly one execution of Finally.

Try and Catch generate separate routes. The HTTP fixture initializes context at the
`cip-chain` entrypoint and retains the snapshot through these nested routes. The
fallback sender must receive the original request ID after the primary override.

## Additional RabbitMQ chains

The generated scenarios cover `propagateContext: false`, a literal context override,
a configured routing key with per-message overrides, manual credentials and vhost, and
MaaS classifier resolution. Context restoration is checked after successful and failed sends.
Broker tests change account state and permissions without replacing the configured credentials.

Dynamic Simple expressions in context overrides, routing keys, and connection parameters need
additional exported configurations. MaaS lookup failures and live MaaS infrastructure are not
covered by the successful lookup scenario. An `InOut` chain needs a supported request/reply
contract before scenarios can define reply handling and timeouts.

TLS, publisher confirms, mandatory returns, and `allowNullBody` are absent from the sender
descriptor's query properties. Testing them as element settings requires catalog or template
changes. [RabbitMqEndpointContainerIT](src/test/java/org/qubership/integration/platform/engine/camel/components/rabbitmq/RabbitMqEndpointContainerIT.java)
covers trusted and untrusted TLS, acks, nacks, and mandatory returns through direct endpoint
configuration. These tests do not establish generated-chain support for those settings.

## GraphQL endpoint tests

[GraphqlCustomEndpointHttpTest](src/test/java/org/qubership/integration/platform/engine/camel/components/graphql/GraphqlCustomEndpointHttpTest.java)
checks HTTP proxy forwarding, a Basic authentication challenge, trusted HTTPS, rejection of
untrusted, expired, and mismatched certificates, and response timeout recovery through the
same producer and HTTP client. These tests configure the endpoint directly; they do not
establish generated-chain support for those settings.

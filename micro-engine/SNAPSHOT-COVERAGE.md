# Generated snapshot coverage

The generated suite imports [test configurations](../integration-build-pipeline/src/test/resources/testConfigurations),
builds their XML through integration-build-pipeline, and executes that XML in micro-engine.
The matrix records assertions defined in the manifests. Test reports determine whether those
assertions pass. Listing an element type does not imply coverage of all its options or protocols.

A scenario ID is scoped to its manifest. Links below identify the manifest; exact scenario IDs can be used with
`snapshot.target` and `snapshot.scenario`. Structural child types share a row with the element that executes them.

The Kafka manifest groups seven chains. Each of its 29 scenarios selects one deployment and starts one broker;
the full suite defines 94 scenarios while avoiding unused deployments and fixtures.
Kafka scenarios contain 263 invocations: 18 Short invocations and 245 across 28 Long scenarios.
Compatible cases share a broker and route while preserving
their individual assertions and recovery checks. The runner stops a scenario at its first unexpected failure.

The RabbitMQ manifest groups 89 invocations into four scenarios across three exported chains.
The functional chain retains four independently configured sender routes. Its 18 Short and
47 Long invocations select their respective entrypoints and share one broker per scenario.
The broker failure scenario contains 22 invocations; the MaaS scenario contains two.
Each invocation checks delivery and verifies that inactive senders did not attempt a send.

The Pub/Sub manifest groups 28 invocations into three scenarios for one exported chain:
two Short invocations, 25 Long invocations sharing an emulator and publisher, and one
OAuth rejection invocation with an empty credentials cache. The combined Long scenario
refreshes its token first, recreates the topic after publication and recovery checks,
and deletes the topic at the end.

## Additional RabbitMQ chains

The generated scenarios cover disabled context propagation, a literal context override,
a configured routing key with per-message overrides, manual credentials and vhost, and
MaaS classifier resolution. Context restoration is checked after successful and failed sends.
Broker tests change account state and permissions without replacing the configured credentials.

Dynamic Simple expressions in context overrides, routing keys, and connection parameters need
additional exported configurations. MaaS lookup failures and live MaaS infrastructure are not
covered by the successful lookup scenario. An `InOut` chain needs a supported request/reply
contract before scenarios can define reply handling and timeouts.

TLS, publisher confirms, mandatory returns, and `allowNullBody` are absent from the sender
descriptor's query properties. Testing them as element settings requires catalog or template
changes. [RabbitMqEndpointContainerIT](src/test/java/org/qubership/integration/platform/engine/camel/components/rabbitmq/RabbitMqEndpointContainerIT.java)
covers trusted and untrusted TLS, acks, nacks, and mandatory returns through direct endpoint
configuration. These tests do not establish generated-chain support for those settings.

These gaps are candidates for new exported configurations and manifest scenarios. Other library element types absent
from the first table also have no claimed generated coverage here. Unit tests and fixture-isolation tests are separate
evidence; they do not fill a missing generated scenario in this matrix.

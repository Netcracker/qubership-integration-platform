# Generated snapshot coverage

The generated suite imports [test configurations](../integration-build-pipeline/src/test/resources/testConfigurations),
builds their XML through integration-build-pipeline, and executes that XML in micro-engine.
The matrix records assertions defined in the manifests. Test reports determine whether those
assertions pass. Listing an element type does not imply coverage of all its options or protocols.

A scenario ID is scoped to its manifest. Links below identify the manifest; exact scenario IDs can be used with
`snapshot.target` and `snapshot.scenario`. Structural child types share a row with the element that executes them.

## Families without generated scenarios

| Element types | Missing coverage |
| --- | --- |
| `http-sender` | A dedicated element scenario, including request options, response handling, and transport errors. |
| `kafka-trigger-2` | Inbound consumption, acknowledgments/offsets, redelivery, and shutdown. |
| `jms-trigger` | Inbound consumption, acknowledgment, redelivery, and reconnection. |
| `rabbitmq-trigger-2` | Inbound consumption, acknowledgments, rejection, and redelivery. |
| `pubsub-trigger` | Subscription delivery, acknowledgment deadlines, redelivery, and shutdown. |
| `scheduler`, `quartz-scheduler` | Trigger timing, misfires, repeated execution, and lifecycle. |
| `sftp-trigger`, `sftp-trigger-2`, `sftp-download`, `sftp-upload` | Remote connection setup, transfer, polling, and failure handling. |

These gaps are candidates for new exported configurations and manifest scenarios. Other library element types absent
from the first table also have no claimed generated coverage here. Unit tests and fixture-isolation tests are separate
evidence; they do not fill a missing generated scenario in this matrix.

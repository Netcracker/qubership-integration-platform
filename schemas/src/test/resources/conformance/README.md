# Conformance corpus

This directory is the parity oracle for operation schema extraction. Each case pairs a raw specification source with the
`specification`, `requestSchema`, and `responseSchemas` that the runtime-catalog import path produced for one operation.
The backend `OperationSchemaExtractor` (plan Tasks 3-5) and the VS Code extension (PR-E) must both reproduce these
expected outputs from the same inputs, so the corpus lives here in the `schemas` module, which both consumers share.

The fixtures were dumped verbatim from a locally seeded PostgreSQL database (`catalog` schema). The expected JSON holds
the stored `jsonb` bundles exactly as persisted — resolved draft-07 schemas keyed by content type, with `$id` and
`#/definitions` references intact. Do not reformat them by hand.

The `grpc-payments` case is the one exception. This stack seeds no `specification_source` row for `.proto` sources, so
its expected JSON is not a database dump. It was generated by running `source.input.proto` through the pure-Java Wire
extractor — the same code the read path uses, which needs no `protoc`. Treat it as machine-generated extractor output:
regenerate it through the extractor rather than editing it by hand.

## Layout

```
conformance/
  <protocol-and-version>-<service>/
    source.input.<ext>          one raw spec per model (json | yaml | wsdl | graphql | proto)
    <operationId>.expected.json  one file per operation of that model
```

The input is shared per model: every `*.expected.json` in a directory extracts from the single `source.input.*` beside
it. This mirrors the extractor contract, which takes a `SystemModel` plus a `(path, method)` match key. Filenames are a
sanitized `operationId` for readability only — the authoritative match key is inside each `*.expected.json`.

## Expected file format

```json
{
  "modelId": "<system model id>",
  "operationId": "<Operation.name>",
  "path": "<Operation.path>",
  "method": "<Operation.method>",
  "sourceHash": "<sha256 of source.input.*, matches specification_source.source_hash>",
  "specification": { ... } | null,
  "requestSchema": { ... } | null,
  "responseSchemas": { ... } | null
}
```

`(path, method)` locates the operation within the source. `sourceHash` is the SHA-256 of the input bytes and equals the
stored `specification_source.source_hash`, so a consumer can confirm it parsed the same source. Schema fields may be
`null`: that is the passthrough behavior for protocols without JSON schemas, and it is deliberately locked here.

## Coverage

38 operations across 10 models. Schema presence follows the protocol:

| Family (directory prefix) | Protocol / spec | Schemas present |
|---|---|---|
| `openapi32` | OpenAPI 3.2 | request + response |
| `openapi31` | OpenAPI 3.1 | request + response |
| `openapi30` | OpenAPI 3.0 | request + response |
| `swagger20` | Swagger 2.0 | request + response |
| `asyncapi30`, `asyncapi26` | AsyncAPI 3.0 / 2.6 | response payload only |
| `grpc` | gRPC / protobuf (`.proto`) | request + response |
| `graphql` | GraphQL SDL | none (specification only) |
| `wsdl` | WSDL / SOAP | none (full passthrough) |

The gRPC read path resolves both schemas from the `.proto` alone through the pure-Java Wire extractor, so the case
covers request and response. It does not exercise the `specification_source` persistence path: this stack seeds no
`.proto` source row, so the expected JSON was extracted directly from `source.input.proto` (see the provenance note
above).

Not covered:

- **Multi-file OpenAPI.** The Java parser cannot resolve cross-file `$ref`s. That case belongs to the extension plan
  (PR-E), which resolves references through `specifications[].filePath`.

## How it loads

`schemas` is not part of the runtime-catalog Maven reactor, so `runtime-catalog/pom.xml` declares a `<testResource>`
that copies this directory to the test classpath under `/conformance` (the `targetPath` matters — the other test
resources land at the classpath root). Tests read cases with
`getClass().getResourceAsStream("/conformance/<dir>/<file>")`. `ConformanceCorpusLoaderTest` walks the tree and asserts
every case is present and well formed.

# testing-service

The one Go module in the repository. `README.md` next to this file covers running and embedding the service; this file
covers the constraints that are easy to break while changing it.

Keep durable notes here. `CLAUDE.md` files are not versioned in this repository, only `AGENTS.md` is, so anything a
future reader needs has to live in this file rather than in a local scratch file. This file is written by hand, as
`engine/AGENTS.md` and `micro-engine/AGENTS.md` are: `apm compile` generates none of the three, so edit them directly.
Every other `AGENTS.md` in the repository is generated.

## Layout

```text
testing-service/
  go.mod  go.sum  .golangci.yml  VERSION  Dockerfile  README.md  AGENTS.md
  service.go            package testingservice — the public surface
  migrations.go         Migrations(), go:embed over migrations/
  migrations/           00000000000100__init.tx.up.sql, 00000000000101__execution.tx.up.sql
  application.yaml      the binary's configuration, not the library's
  cmd/testing-service/  the standalone binary
  docs/                 generated by swag, never edited by hand
  internal/
    config/ model/ dao/ matching/ matching/predicates/ qip/ triggers/ services/ services/importexport/
    controllers/ db/ testsupport/
```

The `internal/` packages are kept in one dependency order. The import graph is consistent with that order but does not
force it: `qip` imports nothing internal, and `matching` imports only `model` and `matching/predicates`. Treat the order
as the convention to add to, not as something the compiler checks. `matching` is also where the values of the
`entity_type` enum are declared, because the data getter table is what dispatches on them; `dao` names none of them:

```text
config → model → dao → matching → qip → triggers → services → controllers → root facade → cmd
```

`DecodeTestingContext` lives in `model` rather than beside the controllers, so that `matching` can decode the header
without importing them. `New` is the one place that normalizes its inputs: it calls `Config.WithDefaults()` and
`Deps.WithDefaults()`, and everything under it takes `cfg` and `deps` already normalized, so no constructor below
repeats a default or guards against a nil logger. The repositories go one step further and take the pagination limit as
a plain `int`, so no repository reads configuration at all.

`TestingContext`, its header name and the standard padded base64 alphabet are a contract with two Java copies, in
`engine/src/main/java/.../service/testing/TestingContext.java` and the same path under `micro-engine/`. Golden literals
in `internal/model/testing_context_test.go` and in both Java `TestingContextTest` classes are what hold the three in
step, so a change here lands in all three.

## Public surface

Package `testingservice` exports one name per thing a host overrides. Adding to this list is a decision, not a
formality: every name here is something a downstream host has to keep working.

| Name | What it is |
| --- | --- |
| `Config` | settings: catalog and engine addresses, poll interval, worker count, lease duration, retention, pagination limit, production flag. No DSN. |
| `(Config).ProductionMode() bool` | reads the tri-state production flag, resolving an unset one |
| `Deps` | `DB`, `Logger`, `HTTPClient`, `CurrentUser` |
| `DB`, `CurrentUserFunc` | aliases so a caller can name the types it implements |
| `New(Config, Deps) (*Service, error)` | wires repositories, services and controllers |
| `(*Service).Mount(fiber.Router)` | registers the routes and the user-context middleware |
| `(*Service).RunExecutor(ctx) error` | runs the executor, the lease sweeper and retention |
| `Migrations() (*migrate.Migrations, error)` | for a host that applies migrations through its own tooling |

`Config` and `Deps` are declared in `internal/config` and surface here as aliases. The root package imports `internal/…`,
so the canonical declarations cannot live in the root.

`Deps.DB` is the single method `GetBunDb(ctx) (*bun.DB, error)` — the only one the DAO calls, and the one the downstream
database client already has, so it satisfies the interface without an adapter. Authorization is injected as an
`http.RoundTripper` on `Deps.HTTPClient`, not as a token the module fetches.

`Config.Production` is the one field that is a pointer, and it has to stay one. `GET /mode` tells the front end to hide
the operations that are unsafe on a live installation, so an installation that names no mode has to be reported as a
live one — which a bare `bool` cannot express, since its zero value is the permissive answer. `WithDefaults` resolves
nil to `true` the way it fills in a non-positive number, and `ProductionMode()` resolves it again for a `Config` that
never went through `WithDefaults`. Inverting the field into a `NonProduction bool` would read as `false` in every
configuration file that means "hide nothing", which is the same trap one field further along.

## The library and the binary

The library registers routes and runs the executor. Everything else belongs to the host:

- `cmd/testing-service` owns the database DSN, schema creation, health, pprof, metrics, route registration and the API
  prefix. Dropping these from the library is what removed three vendor dependencies.
- `Mount` registers relative paths (`/test-cases`, not `/api/v1/test-cases`), so the host chooses the prefix. The binary
  mounts under `/api/v1`, which the nginx rule in `infrastructure/nginx/routes.conf` assumes.
- The generated spec does not follow the prefix: `basePath` is empty and every `@Router` annotation spells out
  `/api/v1/…`, so `docs/` describes the standalone binary. A host that mounts elsewhere serves paths the spec does not
  match, and publishes its own spec instead.
- The routes beside the API belong to the binary too: `/v2/api-docs` and `/swagger-ui/*` serve the same spec as
  `/api/v1/swagger/*`, and `/api-version` answers the version document the ported service served from
  `api-version-info.json`. All three were public in the ported service and its direct callers still ask for them. No
  routing rule in front of this service exposes them, which is why they cost nothing here and why the library must not
  grow them: a host mounts the API on a router of its own and owns everything beside it.
- New infrastructure concerns go in `cmd/`. A health check or a metrics exporter added to the library would be dead
  weight downstream and would pull its dependency into every host.
- No default is written down twice. `defaultAppConfig` fills in what the binary owns, and the shipped
  `application.yaml` and the Helm ConfigMap carry only that plus what an installation has to choose; the library's
  settings are left unset there and picked up from `Config.WithDefaults`.

## Wire compatibility with the ported service

A downstream vendor runs the service this module was ported from, and a separate front-end plan is written against these
endpoints, so what goes over the wire is not ours to improve on its own. Three rules carry that:

- `optionalTime` writes the two CSV timestamp columns with `(*time.Time).String()`, the Go layout
  `2006-01-02 15:04:05.999999999 -0700 MST`, and not RFC 3339. The nil guard around it is ours and has to stay: the
  ported service dereferenced the nil of a pending run and panicked. The layout is theirs, and four exports share the
  writer.
- The routes beside the API and the production default, both above.

A fix to a real defect is still a fix: the run's own id in column 2 of the test case run export, the spreadsheet-formula
escaping, and the nil guard above all changed the bytes on purpose.

## Naming

The DAO surface keeps the initialisms it was ported with — `FindById`, `FindByIds`, `GetDb`, `GetSqlSortingOrder`,
`GetIdFilterConfiguration` — and its pointer-to-slice parameters (`ids *[]uuid.UUID`, `filters *[]model.Filter`).
Both are applied consistently across every repository, service and fake, so changing them is churn without a
behavioral gain. New code goes the Go way instead: `ID`, `IDs`, `URL` and `UUID` in locals, unexported helpers and
struct fields, and a bulk method takes the same pointer-to-slice its siblings take.

## Migrations

- Numbered from 100, like the other modules, because the downstream host keeps its own migrations 01 and 02. Migration
  100 is therefore idempotent per object kind: `create … if not exists` for a table or an index, a `do $$ … exception
  when duplicate_object` block for enum types, `create or replace` for views and trigger functions, `drop trigger if
  exists` before `create trigger`.
- **Migrations must not create the schema.** The downstream schema is provisioned elsewhere and is not named
  `testing_service`; a hardcoded `create schema` would either leave a stray empty schema or fail on a role without
  `CREATE`. The binary creates the schema, and it does so **before** `migrator.Init`, because bun writes its bookkeeping
  table first and that write fails while `search_path` names a schema that does not exist yet.
- **The `.tx.up.sql` suffix is load-bearing.** A file with no `--bun:split` directive runs as a single `ExecContext`,
  and only this suffix wraps it in a transaction. Renaming a migration to `.up.sql` leaves partial DDL behind on
  failure.
- Because a whole file is one statement, it also has to fit inside the socket read deadline. pgdriver defaults that to
  10 seconds and takes the minimum of it and the context deadline, so the default is a ceiling no caller can raise, and
  migration 101 over a populated `test_case_runs` would fail the startup and crash-loop the pod on an `i/o timeout` that
  names nothing. `db.DefaultReadTimeout` and `db.DefaultWriteTimeout` replace it; the DSN parameters `read_timeout` and
  `write_timeout` still win, which is the escape hatch the README points an operator at.
- `Migrations()` builds a fresh `migrate.Migrations` on every call, so a second call cannot register the same set twice.
- A view defined as `select t.*, …` does not gain a new column on its own — PostgreSQL expands `*` at creation time —
  and `create or replace view` can only append columns at the end. Migration 101 drops and recreates
  `test_case_runs_view` for this reason. Any later column added to `test_case_runs` needs the same treatment.
- **Migration 101 requires a stopped executor.** Its data-modifying CTE re-queues every case left `running` and deletes
  that attempt's validation errors. `lease_owner is null` fences the workers of this module, but nothing fences the
  executor that ran before it, which is what produced those rows. Run the migration while that executor is still
  serving and an in-flight attempt loses its errors, runs a second time against the live chain, and is later overwritten
  by the old worker's terminal status. The requirement is stated at the top of the statement in the migration file,
  because that is where an operator meets it.

## Known defect: `test_cases_view` squares the rule counts

`test_cases_view` in `migrations/00000000000100__init.tx.up.sql` joins `matchers` **twice** — once for every rule and
once for the enabled ones — and then counts over the product of the two joins. A test case with three rules, all of
them enabled, comes back with `validation_rule_count` 9 and `enabled_rule_count` 9. The numbers are exact only for a
case with no rules, or with none enabled.

The UI renders what the view returns, so the **Rules** and **Active Rules** columns of the test case lists and the two
counts in the test case details panel are wrong wherever this is. `help/docs/01__Chains/8__Testing/testing.md` records
that as a limitation and points the reader at the editor's Response Validation tab; remove the note there when this is
fixed.

The fix belongs to the view. Count over a single join with `filter (where matcher.enabled)`, or read both counts from
one correlated subquery, so that neither join multiplies the other. Both keep the column list and the column types of
the view, so `create or replace view` is enough — but it goes in a **new** migration, because 100 has shipped and an
installation that already ran it never runs it again.

## The lease-fencing invariant

Work is claimed in two steps inside one transaction. Step 1 locks a `tests_runs` row with `for update skip locked`,
which is what serializes entrants within a run; step 2 claims that run's next `pending` case by `(ordinal, id)` and
stamps `lease_until` and `lease_owner`. A single statement guarded by `not exists` does not serialize anything under
READ COMMITTED: two workers evaluate the guard against their own snapshots and both claim a case of the same run.

`lease_owner` is a fencing token, and **every worker write must carry it**. A stalled worker whose lease was swept is
still running, and a write guarded only by `status = 'running'` would overwrite the row the next owner is working on.
`UpdateOwned` (behind `Finish` and `Skip`), `InsertOwned` (validation errors) and `RenewLease` all take the owner and
report `dao.ErrLeaseLost` when the fence rejects the write. The owner is an explicit parameter and never a context
value, so an unfenced write is visible at the call site.

Two more rules the sweeper depends on:

- The sweep is **one** data-modifying-CTE statement. PostgreSQL rechecks the qualifier at write time, so a single
  statement cannot take a lease that was renewed while it ran; selecting the expired rows and updating them by id
  afterwards can.
- The same statement deletes the reclaimed attempt's validation errors. `validation_errors` carries
  `unique (test_case_run_id, matcher_id)`, so a case that runs again would collide with its own previous attempt on the
  first repeated matcher.

Leases are stamped and compared against the **database** clock (`now() + make_interval(secs => ?)`), so a skewed pod
clock cannot sweep a live lease.

Renewal runs three times per lease so that a case survives a blip, and only `dao.ErrLeaseLost` stops it. Returning on
any error spends that redundancy: one reset connection ends the renewal for good, the lease expires under a worker that
is still running the case, and the sweeper hands the live chain to a second worker.

## An empty selection selects nothing

`SelectionSpecification.Ids` distinguishes three states, and `dao.AddSpecification` is where the distinction is
enforced: `nil` puts no id predicate on the query, a non-empty list becomes `id IN (…)`, and a **present but empty**
list becomes `FALSE`. Dropping the predicate for the empty list instead — which is what the ported code did — turns
every caller that passes an empty selection into a caller that asked for the whole table: `/test-cases/export` and
`/endpoint-mocks/export` dumped the catalog, and `POST /tests-runs/create?from=test_case_runs` with an empty body
started a run over every test case in the installation, each one firing real requests at live chains.

The guard belongs at that layer because the callers are many and the mistake is invisible at the call site. Callers
that can answer without a query still return early — `getTestCasesIds` and the CSV exports do — so an empty request
costs no round trip and keeps its own error (`ErrEmptyTestCaseList`). The destructive bulk paths (`BulkDelete`,
`DeleteByOwnerIds`, `CancelByTestsRuns`) never relied on the specification and guard the empty list themselves.

## Broken matchers

A matcher that cannot be built — a bad regular expression, an unparseable JSON sample, a missing `value` or `pattern`
parameter, or an entity name no request can carry a value under — is handled twice, and the two halves have opposite
defaults:

- `matcherViolations` builds every matcher on create, update and import, so a matcher that cannot be built is a **400**
  at save time. It covers both kinds: the request matchers of an endpoint mock and the response validation rules of a
  test case, which are the same rows under different owners. Disabled matchers are checked too.
- The run paths **degrade** rather than fail, because a row stored before these checks still has to be served. `Call`
  skips the mock carrying such a matcher and logs it: the mocks of one endpoint are answered from a single sorted list,
  so one broken matcher would otherwise 500 every intercepted call on that element, and the engine has no fallback to
  the real endpoint. A skipped mock falls through to the same 404 that an unmatched call gets. The executor records an
  unbuildable validation rule as a validation error against the case run, and the run still finishes.

The schema of a `match_json_schema` matcher is caller input, and the compiler resolves whatever a reference in it names.
`getJsonSchema` therefore installs a loader that refuses every reference outside the schema itself, because the library
default is `FileLoader`. Without it, a stored matcher carrying `{"$ref": "file:///..."}` reports through its own 400
whether a path exists, whether it is readable and what JSON it holds. Keep the refusal free of the URL the compiler
resolved: a relative reference resolves against the working directory of the process.

An entity name belongs to the second kind of mistake and is the one that keeps coming back, because a matcher over a
name nothing can be found under is not obviously broken: `empty` over it holds for every call, so the mock carrying it
answers calls meant for the mocks it outranks. `internal/matching` states each grammar as what a name **may** be — an
RFC 9110 token for a header, any non-blank string for a query parameter, and for a path parameter whatever a literal
`{name}` placeholder can spell, checked by writing the placeholder and reading it back. Extend those checks that way
too; three rounds of review each banned the character the round before had named, and the round after found another.
`TestEntityNameValidationAcceptsExactlyTheMatchableNames` holds the result to the property over the byte space.

## Strict on create, lenient on update

The save-time rules — the matcher checks above, the 100–599 range of a mock response status, and the field-name and
field-value checks on its response headers — are collected as `violation` values rather than raised on the first one.
Each violation carries a key naming the **offending value alone**, not the element carrying it.

`doCreate` refuses any violation. `doUpdate` reads the stored row first and refuses only the violations whose key the
stored row does not already carry, logging the rest as warnings. A row saved before these rules existed still reads
back — an unbuildable matcher is skipped, an unwritable header is left out of the response — and it used to become
uneditable, because an update validates the whole entity: one legacy header with an empty name blocked every other
edit. Introducing a violation is still a 400, and so is replacing one bad value with a different bad value, since that
key was never stored. Import routes through `doCreate` and `doUpdate`, so an archive entry creating an entity is strict
and one updating an existing entity is lenient, which is what a vendor moving its data needs.

Keys are why leniency does not leak. Keying on the element instead — the matcher, the header — would let an update swap
the value under a legacy element for any other bad one; keying on the value lets the caller rename and re-describe the
element while the refused value stays as it was stored. `parametersKey` sorts, so reordering the parameters of a legacy
matcher is still the same violation. A row with several legacy values tolerates each of them on its own and nothing
else.

`doUpdate` therefore reads the stored row **before** it validates. A payload that is invalid for an entity that does
not exist is now a 404 rather than a 400: the lookup is what decides which of the two answers applies.

## Go version ceiling

The `go` directive stays at **1.22**. The downstream build pins `GOTOOLCHAIN=local` to a 1.22 toolchain, so a
dependency that declares `go 1.23` breaks that build even though it builds fine here. Check the directive of anything
you add or upgrade, and record the reason in `go.mod` when you hold a version back. The current pins:

| Dependency | Version | Why |
| --- | --- | --- |
| `github.com/uptrace/bun` and its pg packages | v1.2.1 | v1.2.18 declares `go 1.24` |
| `github.com/gofiber/fiber/v2` | v2.52.15 | v3.0.0 declares `go 1.25` |
| `github.com/knadh/koanf/v2` | v2.1.2 | v2.2.2 declares `go 1.23` |
| `github.com/testcontainers/testcontainers-go` | v0.35.0 | v0.36.0 declares `go 1.23`, and a tidy under it raises this module's directive too |
| `github.com/swaggo/swag` | v1.16.4 | kept in step with the CLI the `go:generate` directive pins |

CI enforces the ceiling twice: the workflows set `GOTOOLCHAIN: local`, and the Dockerfile builds on `golang:1.22-alpine`
with the same variable.

## Testing and linting

```bash
go test ./...                    # the default suite, no Docker needed
go test -tags integration ./...  # PostgreSQL through testcontainers
golangci-lint run                # v1.64.8, the version .golangci.yml is written against
```

Anything that has to exercise real SQL belongs behind the `integration` build tag. Faking the runner alone does not
remove the database, because repositories re-enter through the DAO's context helper and issue real bun queries; unit
tests fake the runner **and** the repository interfaces.

`.golangci.yml` is written against the v1 schema. Super-linter's Go linters are off on purpose — it ships golangci-lint
v2 and points it at a shared config that this file is incompatible with — so `.github/workflows/testing-service-build.yaml`
is the only place Go linting runs.

## Sanitization

Every commit passes `scripts/check-sanitization.sh`, installed as a pre-commit hook, which refuses vendor-internal
identifiers anywhere in the staged content. It reads its token list from a file outside the repository and fails when
that file is missing rather than passing silently. `scripts/check-go-dependencies.sh` is the CI-side net: it asserts
that every module path in `go.mod` and `go.sum` sits under an allowlisted public prefix, which catches a vendor module
without naming one. A new dependency source is an explicit edit to that allowlist.

## Ports and routing

The container listens on **8080** and the local stack exposes it on host port **8095**. The API is served under
`/api/v1`, unlike the Java modules, which serve `/v1`. `/endpoint-mocks/call` is refused by the proxy on purpose: the
engine calls it from inside the network, and nothing outside should.

## Releases

The tag form is **`testing-service/vX.Y.Z`**, with a slash. Every other module in the repository tags as
`<module>-vX.Y.Z`, but the go command resolves a module in a subdirectory only from tags carrying that subdirectory as a
prefix, so the usual form would leave the module unresolvable. `scripts/compute-release-version.sh` keys the form on
`ECOSYSTEM`, and `scripts/build-bom.sh` carries a `tag_prefix` lookup for the same reason. There is no registry upload
for the module itself — the tag is the release. The container image is published as usual:
`.github/workflows/testing-service-release.yaml` builds `testing-service/Dockerfile` and pushes
`ghcr.io/netcracker/qubership-integration-testing-service`. From major version 2 on, the module path itself gains a
`/v2` suffix.

`VERSION` holds the **last released** version, which `scripts/compute-release-version.sh` bumps per release type before
tagging. It starts at `0.0.0`, so the first release has to be cut as a `minor` one to land on `v0.1.0`.
